## 0. 한눈에 보기

```
[바텐더 앱 v3.0] --BLE(Nordic UART, JSON 한 줄 + \n)--> [ESP32] --GPIO--> [4채널 릴레이] --5V--> [수중펌프 ×4]
[PC 시리얼 모니터] --USB(115200bps, 같은 JSON)----------^      (휴대폰 없이도 테스트 가능)
```

| 파일 | 역할 |
|---|---|
| `SmartBartender/SmartBartender.ino` | ESP32 "몸통": BLE, USB 시리얼, 릴레이 GPIO, 플래시(NVS) 저장, LED, 부저, 버튼, 워치독 |
| `SmartBartender/BartenderCore.h` | "두뇌": 명령 해석·검증, 펌프 상태머신(비차단), 이벤트 생성. 하드웨어와 무관 → PC에서 단위 테스트 가능 |
| `SmartBartender/config.h` | **설정 파일**: 핀 번호, 펌프 개수, 안전 한계값, 부저 사용 여부 등. 값 변경은 여기서만 |
| `SmartBartender/WatchdogRelayOff.cpp` | 안전 장치: 워치독이 걸리는 순간 릴레이를 즉시 끔(워치독 인터럽트 훅, 7-3). Arduino IDE 가 자동으로 함께 컴파일 |
| `test/` | PC 단위 테스트(**191개** 케이스 = 펌프 4개 180 + 펌프 8개 11) 소스와 실행 스크립트 |

**핵심 동작 원리**
- 앱이 `{"cmd":"make","steps":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}` 를 보내면
  펌웨어가 `구동시간(ms) = ml ÷ 유량(ml/s) × 1000` 을 계산해 펌프를 켜고 끕니다.
  (유량 기본값 20ml/s → 45ml = 2.25초. 펌프마다 **캘리브레이션**해서 실제 값으로 바꿉니다 → 5장)
- `delay()` 를 쓰지 않는 **millis() 상태머신**이라, 제조 중에도 정지 명령·버튼·통신을 즉시 처리합니다.
- BLE 콜백(블루투스 태스크)은 받은 글자를 줄 단위로 모아 **FreeRTOS 큐**에 넣기만 하고,
  실제 처리는 `loop()` 한 곳에서만 합니다 → 두 태스크가 동시에 펌프 상태를 건드리는 문제가 없습니다.

### v2.1 에서 바뀐 점 (v2.0 → v2.1)
| 항목 | v2.0 | v2.1 |
|---|---|---|
| make 한 펌프 최대 구동시간 | 60초 | **120초** (체크밸브를 달면 유량이 3~6ml/s 로 낮아지기 때문) |
| run 최대 | 60초 | 60초 (그대로, make 와 별도) |
| 같은 펌프 합산 후 300ml 검사 | 없음 (200+200 도 통과) | **합산 후 펌프별 300ml 이하**, 넘으면 `LIMIT` |
| `info` 이벤트 | cal, maxMl, maxStepMl | + **`calSet`**(펌프별 캘리브레이션 여부 0/1), **`maxPumpMs`**(120000) |
| `cal` 이벤트 | cal | + **`calSet`** |
| 안전 감시 | 모든 작업 61초 | 작업별: make 121초 / run 61초 / clean 31초 |
| run/clean 의 ms | 1 이상 | **0 보다 크면** 허용 (SPEC: ms ≤ 0 → `BAD_AMOUNT`) |
| 기타 | | loop 워치독, BLE 구독 상태 정확히 판정, 광고 재시작 재시도, NVS 쓰기 줄이기 (10장) |

## 1. Arduino IDE 설정 (처음 한 번만)

### 1-1. 설치
1. **Arduino IDE 2.x** 설치 (https://www.arduino.cc/en/software)
2. **파일 → 기본 설정(Preferences)** → "추가 보드 관리자 URL" 칸에 아래 주소 붙여넣기
   ```
   https://espressif.github.io/arduino-esp32/package_esp32_index.json
   ```
3. 왼쪽 **보드 매니저** 아이콘 → `esp32` 검색 → **"esp32 by Espressif Systems"** 설치
   - 검증한 버전: **3.3.8** (3.x 버전이면 됨. **2.x 는 BLE API 가 달라 컴파일 오류**가 납니다)
4. 왼쪽 **라이브러리 매니저** 아이콘 → `ArduinoJson` 검색 → **"ArduinoJson by Benoit Blanchon"** 설치
   - 검증한 버전: **7.4.3** (7.x 필수. 6.x 가 깔려 있으면 7.x 로 업데이트)
   - BLE 라이브러리는 ESP32 코어에 들어 있으므로 **따로 설치하지 않습니다.**
5. USB 드라이버: 보드를 꽂았는데 **장치 관리자 → 포트(COM & LPT)** 에 `Silicon Labs CP210x` 가 안 보이면
   Silicon Labs 의 **CP210x USB to UART Bridge VCP 드라이버**를 설치하세요.

### 1-2. 보드 선택 (도구 메뉴)
| 항목 | 값 |
|---|---|
| 보드 | **esp32 → ESP32 Dev Module** |
| Upload Speed | 921600 (업로드가 자주 실패하면 115200) |
| Flash Size | 4MB (32Mb) |
| Partition Scheme | Default 4MB with spiffs (1.2MB APP) — 현재 펌웨어 크기 약 1.13MB(**86%**)로 들어감 |
| Core Debug Level | None |
| 포트 | `COMx` (CP210x 가 잡힌 번호) |

> 나중에 기능을 추가해서 "Sketch too big" 오류가 나면 Partition Scheme 을 **Huge APP (3MB No OTA/1MB SPIFFS)** 로 바꾸세요.

## 2. 하드웨어 연결 요약 (SPEC §1 — 자세한 배선은 `hardware/guide/조립가이드.md`)

| 기능 | ESP32 핀 | 연결 | 주의 |
|---|---|---|---|
| 펌프 1~4 | GPIO **26, 27, 32, 33** | 릴레이 IN1~IN4 | 릴레이는 **LOW = 켜짐(Active-LOW)** |
| (확장) 펌프 5~8 | GPIO 25, 13, 18, 19 | 2번째 릴레이 IN1~IN4 | `config.h` 의 `PUMP_COUNT` 를 5~8 로 |
| 상태 LED | GPIO **2** | GPIO2 → **220Ω** → LED(+), LED(−) → GND | **외부 LED + 220Ω 필수** — DevKitC V4 에는 GPIO2 사용자 LED 가 없음(빨간 전원 LED 만 있음) |
| 부저(선택) | GPIO **23** | 능동 부저 모듈 ONE005 의 I/O | **HIGH = 울림** (`BUZZER_ON_LEVEL 1`, 기본값) |
| 버튼(선택) | GPIO **4** | 버튼 한쪽 → GPIO4, 다른 쪽 → GND | 내부 풀업, 눌림 = LOW |

### 2-1. 릴레이 연결: A안 / B안 (벤치 테스트로 결정)
두 방법 모두 **Active-LOW 라서 펌웨어는 똑같습니다.** 조립 가이드 **STEP2 벤치 테스트**에서
`{"cmd":"run","p":1,"ms":2000}` 으로 릴레이가 확실히 "딸깍" 켜지고 꺼지는지 보고 정합니다.

| | A안 (기본) | B안 (A안이 안 될 때) |
|---|---|---|
| JD-VCC 점퍼 | **뺌** | **다시 끼움** |
| 릴레이 `VCC` | ESP32 **3V3** | 점퍼를 통해 **5V** (3V3 선은 **뽑음**) |
| 릴레이 `JD-VCC` | 5V | 5V |
| 릴레이 `IN1~4`, `GND` | GPIO 직결, GND 공통 | 그대로 |
| 장점 | 3.3V 신호로 **확실히 꺼짐** | 입력 전류가 커서 **확실히 켜짐** |
| 판정 | 릴레이가 확실히 켜지면 A안 유지 | A안에서 표시 LED 가 희미하거나 딸깍 소리가 없으면 B안 |

> ⚠️ **B안에서는 릴레이 `VCC` 를 절대 ESP32 `3V3` 에 연결하지 마세요.** 점퍼가 꽂힌 상태에서는 5V 가
> ESP32 의 3.3V 쪽으로 들어가 보드가 상할 수 있습니다.

### 2-2. 부팅할 때 펌프가 튀지 않게 (펌웨어가 하는 일)
- `setup()` 맨 처음에 릴레이 핀의 출력값을 **HIGH(꺼짐)로 먼저 써 두고**(`gpio_set_level`) → 출력 모드로 전환(`pinMode`)
  → 한 번 더 HIGH(`digitalWrite`). (ESP32 코어 3.x 는 `pinMode` 전의 `digitalWrite` 를 무시하기 때문)
- 전원을 켠 직후~`setup()` 전, 업로드 중, EN(리셋) 버튼을 눌렀을 때는 칩 전체가 리셋되어 핀이 "입력(연결 안 됨)" 상태라
  릴레이에 전류가 흐르지 않아 **꺼져 있습니다.**
- 단, **워치독·패닉(오류)으로 인한 재시작은 CPU 만 리셋**하므로 핀 출력값이 그대로 남습니다(펌프가 켜져 있었다면 LOW=켜짐 유지).
  그래서 펌웨어가 워치독 인터럽트에서 릴레이를 **즉시 끄고**, 재부팅 후 `setup()` 에서 다시 OFF 로 초기화합니다(7-3).

## 3. 업로드 방법

1. Arduino IDE 에서 **`firmware/SmartBartender/SmartBartender.ino`** 를 엽니다.
   - 폴더 이름과 `.ino` 파일 이름이 같아야 합니다. `config.h`, `BartenderCore.h` 가 같은 폴더에 있어야 탭으로 함께 열립니다.
2. ⚠️ **업로드 전에 외부 5V 전원을 분리하세요.**
   - 기기에 조립된 상태라면 **5V 어댑터를 뽑거나(SW1 끄기)**, ESP32 의 **5V(VIN) 핀으로 가는 선을 빼세요.**
   - USB 5V 와 어댑터 5V 가 동시에 들어가면(이중 전원) PC USB 포트나 보드가 손상될 수 있고, 업로드 중 펌프가 튈 수 있습니다.
3. **업로드(→) 버튼**을 누릅니다.
4. 아래 창에 `Connecting.....` 이 나오면 보드의 **BOOT 버튼을 누르고 있다가**, `Writing at 0x...` 가 나오기 시작하면 손을 뗍니다.
   (대부분의 DevKitC 는 자동으로 되지만, 안 되면 이 방법을 쓰세요.)
5. `Hard resetting via RTS pin...` 이 나오면 완료. 보드의 **EN(RST) 버튼**을 한 번 누르면 새 펌웨어로 재시작합니다.

> 캘리브레이션 값은 플래시의 별도 영역(NVS)에 저장되므로 **펌웨어를 다시 올려도 유지**됩니다.
> (도구 → Erase All Flash Before Sketch Upload → Enabled 로 올리면 초기화되고 `calSet` 이 모두 0 이 됩니다.)

## 4. 시리얼 모니터로 테스트하기 (휴대폰 없이)

1. 업로드 후 **도구 → 시리얼 모니터** (오른쪽 위 돋보기 아이콘)
2. 오른쪽 아래 설정: **115200 baud**, 줄 끝 **"새 줄(New Line)"** (또는 Both NL & CR)
3. 보드의 EN 버튼을 누르면 이런 부팅 메시지가 나옵니다.
   ```
   # ===========================================
   # AI 스마트 바텐더 펌웨어 v2.1.0
   # 장치 이름: SmartBartender-A1B2 / 펌프 4개
   # 리셋 원인: 전원 켜짐
   # 펌프 1 유량 20.00 ml/s (기본값 - 캘리브레이션 전, 실제보다 적게 나올 수 있음)
   # 펌프 2 유량 4.50 ml/s (캘리브레이션 완료)
   # 펌프 3 유량 20.00 ml/s (기본값 - 캘리브레이션 전, 실제보다 적게 나올 수 있음)
   # 펌프 4 유량 20.00 ml/s (기본값 - 캘리브레이션 전, 실제보다 적게 나올 수 있음)
   # BLE 광고 시작. 시리얼 모니터(115200, 줄바꿈 'Newline')에서도 명령 가능:
   # ===========================================
   {"ev":"info","fw":"2.1.0","name":"SmartBartender-A1B2","pumps":4,"cal":[20,4.5,20,20],"calSet":[0,1,0,0],"maxMl":500,"maxStepMl":300,"maxPumpMs":120000,"state":"idle"}
   ```
   - `#` 으로 시작하는 줄 = 사람이 읽는 **로그**
   - `{` 로 시작하는 줄 = 앱이 받는 것과 **똑같은 이벤트 JSON**
   - BLE 로 들어온 명령도 `# <- BLE: {...}` 로 시리얼에 찍히므로, 앱 디버깅에도 쓸 수 있습니다.
   - `calSet` 이 0 인 펌프는 아직 캘리브레이션 전입니다. 앱이 "캘리브레이션 전 — 실제보다 적게 나올 수 있어요" 배너를 띄웁니다.

4. 입력창에 아래 명령을 **한 줄씩 복사해서 Enter**.

### 명령 예시 모음

| 하고 싶은 일 | 입력 | 예상 응답 |
|---|---|---|
| 기기 정보 | `{"cmd":"hello"}` | `{"ev":"info",...,"calSet":[0,0,0,0],...,"maxPumpMs":120000,...}` |
| 현재 상태 | `{"cmd":"status"}` | 부팅 직후: `{"ev":"status","state":"idle","job":null,"last":null}` / 작업이 끝난 뒤에는 `last` 에 그 결과 (7-7) |
| 연결 확인 | `{"cmd":"ping"}` | `{"ev":"pong","up":123456}` |
| 유량표 보기 | `{"cmd":"getcal"}` | `{"ev":"cal","cal":[20,20,20,20],"calSet":[0,0,0,0]}` |
| 펌프1 을 3초 구동 (프라이밍) | `{"cmd":"run","p":1,"ms":3000}` | `ack` → `progress`… → `step` → `done` |
| 펌프1 을 10초 구동 (캘리브레이션 측정) | `{"cmd":"run","p":1,"ms":10000}` | `ack`(totalMs 10000) → … → `done` |
| 모든 펌프 차례로 5초씩 (세척) | `{"cmd":"clean","ms":5000}` | `ack`(totalMs 20900) → … → `done` |
| 펌프2 유량 4.5ml/s 저장 | `{"cmd":"setcal","p":2,"mlps":4.5}` | `{"ev":"cal","cal":[20,4.5,20,20],"calSet":[0,1,0,0]}` |
| 레시피 제조 (순차) | `{"cmd":"make","id":"t1","mode":"seq","steps":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}` | 아래 참고 |
| 레시피 제조 (동시) | `{"cmd":"make","id":"t2","mode":"par","steps":[{"p":1,"ml":30},{"p":2,"ml":30}]}` | `ack` → … → `done` |
| 비상 정지 | `{"cmd":"stop"}` | 제조 중: `{"ev":"stopped","id":"t1","reason":"user","dispensed":[{"p":1,"ml":12.3}]}` / 대기 중: `status` |

순차 제조 예시의 실제 출력(유량 20ml/s 기준):
```
{"ev":"ack","id":"t1","kind":"make","totalMs":4075}           ← 예상 4.075초 (2.25초 + 휴지 0.3초 + 1.525초)
{"ev":"progress","id":"t1","p":1,"ml":45,"doneMl":5,"pct":6}   ← 0.25초마다
...
{"ev":"step","id":"t1","p":1,"ml":45}                          ← 펌프1 완료
{"ev":"progress","id":"t1","p":3,"ml":30.5,"doneMl":0,"pct":59}
...
{"ev":"step","id":"t1","p":3,"ml":30.5}
{"ev":"done","id":"t1","kind":"make","ms":4075,"dispensed":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}
```

오류 응답 예시 (일부러 틀려 보기):

| 입력 | 응답 code |
|---|---|
| `{"cmd":"make","steps":[{"p":1,"ml":0}]}` | `BAD_AMOUNT` (0ml 불가) |
| `{"cmd":"make","steps":[{"p":1,"ml":300.1}]}` | `LIMIT` (재료 1개 최대 300ml) |
| `{"cmd":"make","steps":[{"p":1,"ml":200},{"p":1,"ml":200}]}` | `LIMIT` (**같은 펌프 합계** 400ml > 300ml, v2.1) |
| `{"cmd":"make","steps":[{"p":1,"ml":300},{"p":2,"ml":200.1}]}` | `LIMIT` (총량 최대 500ml) |
| `{"cmd":"make","steps":[{"p":5,"ml":10}]}` | `BAD_PUMP` (펌프는 1~4) |
| `{"cmd":"make","mode":"fast","steps":[{"p":9,"ml":10}]}` | `BAD_JSON` (mode 검사가 펌프 검사보다 먼저) |
| `{"cmd":"run","p":1,"ms":60001}` | `LIMIT` (run 최대 60초) |
| `{"cmd":"make",` | `BAD_JSON` |
| `{"cmd":"dance"}` | `UNKNOWN_CMD` |
| 제조 중에 또 `make` | `BUSY` (진행 중 제조는 계속됨) |
| 1024바이트보다 긴 줄 | `TOO_LONG` |

> 💡 펌프를 연결하지 않아도 **릴레이 모듈의 LED 가 켜지고 "딸깍" 소리**가 나는지로 동작을 확인할 수 있습니다.

## 5. BLE(블루투스)로 테스트하기 — 앱 없이 (안드로이드)

### 방법 A. Serial Bluetooth Terminal (가장 편함)
1. Play 스토어에서 **"Serial Bluetooth Terminal"** (Kai Morich) 설치
2. 앱 왼쪽 메뉴 → **Devices** → 위쪽 **"BLUETOOTH LE"** 탭 → **SCAN**
3. **SmartBartender-XXXX** 선택 → 자동으로 Nordic UART 로 연결 (기기의 LED 가 깜빡임 → **계속 켜짐**으로 바뀜)
4. 메뉴 → Settings → **Send** → Newline 을 **LF** 로 설정
5. 아래 입력창에 `{"cmd":"hello"}` 입력 → 전송 → `{"ev":"info",...}` 가 한 줄로 보이면 성공
6. 4장의 명령 예시를 그대로 보내 볼 수 있습니다.

### 방법 B. nRF Connect for Mobile (자세한 확인용)
1. **nRF Connect** 실행 → **SCAN** → `SmartBartender-XXXX` 의 **CONNECT**
   - 응답이 20바이트씩 잘려 보이면 오른쪽 위 **⋮ 메뉴 → Request MTU → 247** (그래도 펌웨어가 조각으로 나눠 보내므로 내용은 같음)
2. **Nordic UART Service** (`6E400001-...`) 펼치기
3. **TX Characteristic** (`6E400003-...`) 오른쪽의 **알림 아이콘(↓ 여러 개)** 을 눌러 구독(Notify ON)
   — **이걸 먼저 해야 응답이 옵니다.** 구독 전에 생긴 이벤트는 BLE 로 보내지 않고 버립니다(시리얼에는 출력됨).
   연결할 때마다 구독은 초기화되므로 **다시 연결하면 다시 눌러야** 합니다.
4. **RX Characteristic** (`6E400002-...`) 오른쪽 **↑(Write)** → 형식을 **TEXT(UTF-8)** 로 선택 → 아래 JSON 입력 → SEND
   - 줄바꿈(\n)을 넣기 어려워도 괜찮습니다. 펌웨어가 `{ }` 괄호가 닫히는 것으로 명령 끝을 알아냅니다.
5. TX 값 또는 **LOG** 탭에서 응답 확인 (긴 응답은 여러 조각으로 나뉘어 표시될 수 있음)

nRF Connect 로 차례대로 보내 볼 JSON (v2.1):

| 순서 | RX 에 보낼 TEXT | TX 로 오는 응답 (예) |
|---|---|---|
| ① | `{"cmd":"hello"}` | `{"ev":"info","fw":"2.1.0","name":"SmartBartender-A1B2","pumps":4,"cal":[20,20,20,20],"calSet":[0,0,0,0],"maxMl":500,"maxStepMl":300,"maxPumpMs":120000,"state":"idle"}` |
| ② | `{"cmd":"getcal"}` | `{"ev":"cal","cal":[20,20,20,20],"calSet":[0,0,0,0]}` |
| ③ | `{"cmd":"run","p":1,"ms":3000}` | `{"ev":"ack","id":"run","kind":"run","totalMs":3000}` → progress… → `{"ev":"done","id":"run","kind":"run","ms":3000,...}` |
| ④ | `{"cmd":"run","p":1,"ms":10000}` | 10초 구동 (나온 양을 계량컵으로 측정, 예: 45ml) |
| ⑤ | `{"cmd":"setcal","p":1,"mlps":4.5}` | `{"ev":"cal","cal":[4.5,20,20,20],"calSet":[1,0,0,0]}` ← 펌프1 calSet 이 1 로 |
| ⑥ | `{"cmd":"make","id":"t1","steps":[{"p":1,"ml":30}]}` | `{"ev":"ack","id":"t1","kind":"make","totalMs":6667}` → … → `done` |
| ⑦ | `{"cmd":"stop"}` | 제조 중이면 `stopped`, 대기 중이면 `{"ev":"status","state":"idle","job":null,"last":{"id":"t1","kind":"make","result":"done","dispensed":[{"p":1,"ml":30}]}}` (⑥ 이 끝난 뒤) |
| ⑧ | `{"cmd":"make","steps":[{"p":1,"ml":200},{"p":1,"ml":200}]}` | `{"ev":"error","code":"LIMIT","msg":"펌프 1 의 합계 400.0ml 가 최대 300ml 를 넘습니다"}` |

> 휴대폰의 **블루투스 설정 화면에서 "페어링"하지 마세요.** 앱(또는 테스트 앱)에서 직접 연결합니다.
> 한 번에 **한 대의 휴대폰만** 연결됩니다. 다른 폰이 연결돼 있으면 목록에 안 보입니다.
> 연결이 끊기면 0.5초 뒤 자동으로 다시 광고합니다(실패하면 2초마다 재시도).

## 6. 유량 캘리브레이션 (정확한 양을 위해 꼭 하세요)

펌프마다, 튜브 길이·높이, 체크밸브, 액체의 끈적임(시럽 등)에 따라 1초에 나오는 양이 다릅니다.
**체크밸브를 단 상태에서는 약 3~6 ml/s(추정)** 로, 기본값 20 ml/s 보다 훨씬 적습니다.
기본값을 그대로 쓰면 **덜 나오는 쪽(안전)** 이지만 맛이 달라지므로, 펌프별로 꼭 측정하세요.
(앱의 "캘리브레이션 마법사"도 아래와 똑같은 명령을 사용합니다.)

**준비물**: 계량컵(또는 주방 저울: 물 1g ≈ 1ml), 빈 컵, 버릴 컵

### 권장 절차 (펌프 1개당 약 3분)
1. **용기를 반쯤 채웁니다.** 실제로 쓸 액체(또는 물)를 용기의 **절반 정도** 넣습니다.
   *왜?* 액면 높이에 따라 펌프가 올려야 하는 높이가 달라져 유량이 조금씩 바뀝니다. 반쯤 찬 상태가 "평균"입니다.
2. **프라이밍(튜브 채우기)**: 버릴 컵을 노즐 아래 두고
   `{"cmd":"run","p":1,"ms":3000}` → 노즐에서 액체가 **끊김 없이** 나올 때까지 반복 (튜브 속 공기 제거)
3. **측정**: 빈 계량컵을 노즐 아래 두고
   `{"cmd":"run","p":1,"ms":10000}` → **10초** 동안 나온 양을 잽니다. (예: 45ml)
4. **계산**: 유량(ml/s) = 나온 양 ÷ 10 = 45 ÷ 10 = **4.5**
5. **저장**: `{"cmd":"setcal","p":1,"mlps":4.5}`
   → 응답 `{"ev":"cal","cal":[4.5,20,20,20],"calSet":[1,0,0,0]}` — 펌프1 의 **`calSet` 이 1** 이 되면 저장 완료
6. **확인**: `{"cmd":"make","id":"chk","steps":[{"p":1,"ml":30}]}` → 30ml 근처(±5%)로 나오면 성공
7. 펌프 2, 3, 4 도 같은 방법으로 반복. 정확도를 높이려면 3~5를 2~3번 해서 평균을 쓰세요.

- 저장한 값은 전원을 꺼도 유지됩니다 (ESP32 NVS, 네임스페이스 `bartender`, 키 `mlps1`~`mlps8`).
  부팅 때 키가 있으면 그 펌프의 `calSet` = 1, 없으면 0 (기본값 20ml/s 사용 중).
- 허용 범위는 **0.5 ~ 100 ml/s** (밖이면 `BAD_AMOUNT`). 액체 종류나 튜브를 바꾸면 다시 측정하세요.
- 한 펌프 구동시간은 **최대 120초**입니다. 유량이 2.5 ml/s 보다 낮으면 300ml 에 120초가 넘어 `LIMIT` 오류가 납니다.
  (예: 유량 0.5 에서 60ml = 정확히 120초 → 통과, 60.1ml → `LIMIT`)

## 7. 동작 규칙 요약

### 7-1. make 검증 순서 (SPEC §2.3 — 펌웨어·앱·데모 기기 모두 같은 순서, 위에서부터)
| 순서 | 검사 | 위반 시 |
|---|---|---|
| ① | `mode` 가 `"seq"` / `"par"` / 생략 중 하나 | `BAD_JSON` |
| ② | `steps` 가 있고 비어 있지 않음 | `BAD_AMOUNT` |
| ③ | `steps` 8개 이하 | `LIMIT` |
| ④ | step 마다 (앞에서부터) `p` 가 1 ~ PUMP_COUNT 정수 → `ml` 이 0보다 큰 숫자 → `ml` ≤ 300 | `BAD_PUMP` → `BAD_AMOUNT` → `LIMIT` |
| ⑤ | 같은 펌프는 **합산** | — |
| ⑥ | 합산 후 **펌프별 ≤ 300ml** | `LIMIT` |
| ⑦ | 총합 ≤ 500ml | `LIMIT` |
| ⑧ | 펌프별 구동시간(ml ÷ 유량) **≤ 120초** | `LIMIT` |

- 제조 중(running)에 make / run / clean 이 오면 검증보다 먼저 `BUSY` (진행 중인 제조는 그대로 계속).
- 검증에 실패하면 **펌프는 하나도 켜지지 않습니다.**

### 7-2. 그 밖의 명령
| 명령 | 규칙 | 위반 시 |
|---|---|---|
| `run` | `p` = 1 ~ PUMP_COUNT 정수, 0 < `ms` ≤ 60000 | p 오류 `BAD_PUMP`, ms 숫자 아님/≤0 `BAD_AMOUNT`, 60000 초과 `LIMIT` |
| `clean` | 0 < `ms` ≤ 30000 (펌프마다 차례로) | ms 숫자 아님/≤0 `BAD_AMOUNT`, 30000 초과 `LIMIT` |
| `setcal` | `p` 정수, 0.5 ≤ `mlps` ≤ 100 | `BAD_PUMP` / `BAD_AMOUNT` |

### 7-3. 안전 장치
- 릴레이는 **Active-LOW**(LOW=켜짐). 부팅 시 핀을 먼저 HIGH(꺼짐)로 만든 뒤 출력으로 바꿔 부팅 순간 펌프가 튀지 않습니다(2-2).
- **소프트웨어 감시**: 어떤 펌프든 **(작업 상한 + 1초) 이상** 켜져 있으면 전부 끄고 `stopped`(reason `"error"`) + `error/LIMIT`.
  상한은 make **120초**(→121초), run **60초**(→61초), clean **30초**(→31초). 정상이라면 절대 걸리지 않는 최후의 안전장치입니다.
- **loop 워치독**: 펌웨어가 어딘가에서 멈춰 `loop()` 가 5초 넘게 돌지 못하면 ESP32 가 스스로 재시작합니다
  (시리얼 부팅 메시지 `리셋 원인: 워치독 재시작`).
  - 워치독·패닉 재시작은 **CPU 만 리셋**하고 핀 출력값은 그대로 두므로, "재시작하면 저절로 꺼진다"에 기대지 않습니다.
    워치독 시간이 초과되는 순간 **워치독 인터럽트에서 모든 릴레이를 즉시 끄고**(`WatchdogRelayOff.cpp` 의 `esp_task_wdt_isr_user_handler`) 재시작하며,
    재부팅 후 `setup()` 에서 다시 OFF 로 초기화합니다. 즉 펌웨어가 멈추면 약 5초(워치독 시간) 뒤 펌프가 꺼집니다.
  - 전원 투입·EN(리셋) 버튼·브라운아웃(전압 강하) 리셋은 칩 전체가 리셋되어 핀이 입력(꺼짐)이 되므로 문제없습니다.
  - 워치독이 아닌 **다른 원인의 크래시(패닉)** 는 이 처리가 없어, 재부팅해 `setup()` 이 돌 때까지
    **약 1초 안팎**(패닉 로그 출력·코어덤프 저장·부팅 시간, 추정치) 펌프가 더 돌 수 있습니다.
- **물리 버튼**: 제조 중 누르면 즉시 비상정지.

### 7-4. 제조 모드
- **순차(seq, 기본)**: 펌프를 하나씩 → 끝나면 0.3초 쉬고 다음 펌프. 전압이 안정적이고 양이 정확합니다.
- **병렬(par)**: 펌프들을 **0.1초 간격으로 차례로 켜고**(기동 전류 분산, `PAR_STAGGER_MS`) 각자 자기 시간이 되면 끕니다. 빠르지만 전원 부담이 큽니다.

### 7-5. 버튼 / LED / 부저
| 장치 | 동작 |
|---|---|
| 버튼 (GPIO4 ↔ GND) | **제조 중 누르면 즉시 비상정지** (`stopped`, reason `"button"`). 대기 중 짧게 누르면 '삑' + 상태 출력 |
| 버튼 길게(1.5초) | `config.h` 의 `BUTTON_REPEAT_LAST 1` 일 때만: 마지막 레시피 다시 제조 (기본 꺼짐). 다시 만든 잔은 **새 id `btn`+기동 후 ms**(예: `btn123456`)로 `ack`·`done` 등을 보냄 → 7-7 |
| 상태 LED (GPIO2, 외부 LED + 220Ω) | 천천히 깜빡(1초) = 연결 대기 / 계속 켜짐 = 앱 연결됨 / 빠르게 깜빡 = 제조 중 |
| 부저 (GPIO23, HIGH = 울림) | 완료 '삐-삐', 정지 '삐----', 부팅·버튼 '삑' |

### 7-6. 연결이 끊기면?
- 진행 중인 제조는 **정해진 양만큼 끝까지** 수행합니다(정해진 시간만 켜지므로 안전). 물리 버튼으로 언제든 정지 가능.
- 0.5초 뒤 자동으로 다시 광고하므로(실패 시 2초마다 재시도), 앱에서 재연결 후 `{"cmd":"status"}` 로 상태를 확인합니다.
  끊긴 동안 작업이 끝났다면 `status` 의 **`last`** 에 그 결과(완료/중단·나온 양)가 들어 있습니다 → 7-7.

### 7-7. status 의 `last` — 마지막으로 끝난 작업 (SPEC §2.4, v2.1)
`status` 이벤트에는 **부팅 후 마지막으로 끝난 작업**(make / run / clean)의 결과가 `last` 로 함께 옵니다.
앱은 BLE 가 끊긴 사이에 끝난 제조의 결과를 재연결 후 이것으로 확인해 기록·잔량 차감을 합니다.

| 항목 | 내용 |
|---|---|
| `last` | 끝난 작업이 없으면(부팅 직후) `null` |
| `last.id` / `last.kind` | 그 작업의 id 와 종류 (`make` 는 레시피 id, `run`·`clean` 은 id 도 `"run"`·`"clean"`) |
| `last.result` | `"done"`(끝까지 완료) 또는 `"stopped"`(중단) |
| `last.reason` | `stopped` 일 때만: `"user"`(앱 stop) / `"button"`(물리 버튼) / `"error"`(안전 감시) |
| `last.dispensed` | 그 작업의 `done` / `stopped` 이벤트와 **글자까지 똑같은 값**(같은 반올림, `stopped` 는 0ml 펌프 생략) |

- 제조 중(`running`)에 받은 `status` 의 `last` 는 **지금 작업 바로 전에** 끝난 작업입니다.
- `BUTTON_REPEAT_LAST 1` 빌드에서 버튼으로 다시 만든 잔은 앱이 보낸 원래 작업과 다른 작업이라 **새 id(`btn`+기동 후 ms)** 를 씁니다.
  그래서 그 잔이 끝난 뒤의 `last.id` 는 원래 작업 id 와 다르고, 앱은 원래 작업을 "결과 확인 필요"로 처리합니다
  (원래 id 를 다시 쓰면 '다른 잔의 결과'를 '원래 작업의 결과'로 잘못 기록하게 됨).
- 검증 오류(`error`), `BUSY` 로 거절된 명령, 대기 중 `stop`·`ping`·`setcal` 등은 `last` 를 바꾸지 않습니다.
- 전원을 끄거나 재부팅하면 `last` 는 `null` 로 돌아갑니다(플래시에 저장하지 않음).
  → 앱은 `last` 가 없거나 id 가 다르고 `pong.up`(기동 후 시간)이 작업 시작 후 경과시간보다 짧으면 "재부팅으로 중단(양 모름)" 으로 판단합니다(SPEC §2.4).

실제 출력 예 (유량 20ml/s, PC 테스트 코드로 펌웨어 로직을 그대로 실행한 결과):
```
{"ev":"status","state":"idle","job":null,"last":null}                                   ← 부팅 직후
{"ev":"done","id":"t1","kind":"make","ms":4075,"dispensed":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}
{"ev":"status","state":"idle","job":null,"last":{"id":"t1","kind":"make","result":"done","dispensed":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}}
{"ev":"status","state":"running","job":{"id":"t2","kind":"make","pct":29},"last":{"id":"t1","kind":"make","result":"done","dispensed":[{"p":1,"ml":45},{"p":3,"ml":30.5}]}}
{"ev":"stopped","id":"t2","reason":"user","dispensed":[{"p":1,"ml":22.4}]}
{"ev":"status","state":"idle","job":null,"last":{"id":"t2","kind":"make","result":"stopped","reason":"user","dispensed":[{"p":1,"ml":22.4}]}}
```

- 가장 긴 이벤트는 제조 중 `status`(job + last)입니다. 펌프 8개 · id 40바이트에서도 이론상 최대 516바이트로
  펌웨어 출력 버퍼(640바이트, `OUT_BUF_SIZE`) 안에 들어갑니다(PC 테스트 실측 최대 440바이트).
  BLE 로는 (MTU−3) 바이트씩 나뉘어 가고 앱이 `\n` 까지 모아서 읽습니다.

## 8. 설정 바꾸기 (`config.h`)

| 설정 | 기본값 | 설명 |
|---|---|---|
| `PUMP_COUNT` | 4 | 펌프 개수(1~8). 5~8번은 GPIO 25, 13, 18, 19 (두 번째 릴레이 모듈) |
| `PUMP_PINS` | 26,27,32,33,25,13,18,19 | 펌프 → GPIO 매핑 (SPEC 과 같아야 함) |
| `ENABLE_BUZZER` | 1 | 부저 사용 여부 |
| `BUZZER_ON_LEVEL` | 1 | 1 = HIGH 에 울림(ONE005). LOW 트리거 부저로 바꿨을 때만 0 |
| `BUTTON_REPEAT_LAST` | 0 | 버튼 길게 눌러 마지막 레시피 다시 만들기 |
| `MAX_PUMP_MS` | 120000 | make: 펌프 1개 최대 구동시간(ms). info 의 `maxPumpMs` |
| `MAX_RUN_MS` | 60000 | run 최대 구동시간(ms) |
| `CLEAN_MAX_MS` | 30000 | clean 펌프당 최대(ms) |
| `SEQ_GAP_MS` | 300 | 순차 모드 펌프 사이 휴지 |
| `PAR_STAGGER_MS` | 100 | 병렬 모드 펌프 기동 간격 (0 = 완전 동시) |
| `DEFAULT_MLPS` | 20.0 | 캘리브레이션 전 기본 유량 (실제보다 커서 덜 나오는 쪽 = 안전) |
| `ENABLE_LOOP_WDT` | 1 | loop 워치독 (디버깅할 때만 0) |

> 한계값(300ml, 500ml, 120초 등)은 SPEC 의 계약값이라 앱·데모 기기와 함께 바뀌어야 합니다. SPEC 을 먼저 고치세요.

## 9. 문제 해결

| 증상 | 원인 / 해결 |
|---|---|
| **펌프가 켜질 때 ESP32 가 재부팅** (시리얼에 `Brownout detector was triggered` 또는 부팅 메시지 `리셋 원인: 브라운아웃`) | 펌프 기동 순간 전압이 떨어진 것. ① 5V 레일에 **1000µF 16V 커패시터**(극성 주의) ② 펌프마다 **1N4007 다이오드**(띠 → 펌프+) ③ 전원선은 굵은 선으로 짧게, GND 공통 ④ **순차(seq) 모드** 사용 ⑤ USB 전원만으로 펌프를 돌리지 말고 5V 4A 어댑터 사용 |
| **업로드 실패** `Failed to connect to ESP32` / `No serial data received` | ① `Connecting...` 때 **BOOT 버튼 누르고 있기** ② **충전 전용이 아닌 데이터용** USB 케이블 ③ 포트 번호 확인, CP210x 드라이버 설치 ④ 시리얼 모니터 등 다른 프로그램이 포트를 쓰고 있으면 닫기 ⑤ Upload Speed 115200 |
| **릴레이가 꺼지지 않음** (계속 딸깍 상태/LED 켜짐) | **A안**: ① JD-VCC 점퍼를 뺐는지 ② `VCC` = ESP32 3V3, `JD-VCC` = 5V, GND 공통인지 (점퍼 없이 `VCC` 를 5V 에 꽂으면 3.3V HIGH 로 완전히 안 꺼질 수 있음) / **B안**: 점퍼가 꽂혀 있고 3V3 선이 **빠져** 있는지 / 공통: IN1~IN4 가 GPIO 26/27/32/33 에 맞게 꽂혔는지, `{"cmd":"stop"}` 으로도 안 꺼지면 배선 문제 |
| **릴레이가 안 켜지거나 희미함** (표시 LED 가 약하고 딸깍 소리가 없음) | A안에서 3.3V 입력 전류가 부족한 것 → **B안**으로 바꾸기(2-1). 그 밖에 JD-VCC(5V) 미연결, GND 미연결, 핀 번호 틀림. `{"cmd":"run","p":1,"ms":2000}` 로 1개씩 확인 |
| **상태 LED 가 전혀 안 켜짐** | DevKitC V4 에는 GPIO2 LED 가 없습니다. **GPIO2 → 220Ω → LED(+), LED(−) → GND** 로 외부 LED 를 달았는지, LED 방향(긴 다리 = +) 확인 |
| **휴대폰에서 BLE 가 안 보임** | ① 시리얼 부팅 메시지로 펌웨어 실행 확인 ② 다른 폰이 이미 연결돼 있으면 광고를 안 함 (LED 가 계속 켜져 있음) → 그 연결을 끊기 ③ 안드로이드: 블루투스 ON + **'근처 기기' 권한**(Android 12+) 또는 **위치 ON**(Android 11 이하) ④ 폰 블루투스 설정에서 페어링하지 말 것 ⑤ 폰 블루투스를 껐다 켜서 캐시 초기화 ⑥ EN 버튼으로 ESP32 재시작 |
| **연결은 되는데 응답이 안 옴** | TX(`6E400003`) **알림 구독(Notify ON)** 을 먼저 해야 합니다. 구독 전 이벤트는 버려지고, 다시 연결하면 구독도 다시 해야 합니다. |
| `LIMIT` "펌프 N 구동시간 …초가 최대 120초를 넘습니다" | 그 펌프의 유량값이 너무 낮거나 양이 많음. 캘리브레이션 값 확인(`getcal`), 양 줄이기 |
| `LIMIT` "펌프 N 의 합계 …ml 가 최대 300ml" | 같은 펌프가 레시피에 여러 번 나와 합계가 300ml 를 넘음 |
| **양이 부정확함** | 6장 캘리브레이션 다시(용기 반쯤 채운 상태에서), 사용 전 프라이밍, 튜브 꺾임·공기 확인, 체크밸브 방향(화살표 = 노즐 쪽), 노즐을 용기 액면보다 높게(사이펀 방지) |
| 부팅 메시지 `리셋 원인: 워치독 재시작` | 펌웨어가 5초 넘게 멈췄다가 자동 재시작된 것. 반복되면 시리얼 로그(재시작 직전 메시지)를 저장해 두세요 |
| **부저가 계속 울림** | LOW 트리거 부저를 쓰는 경우 → `config.h` 에서 `BUZZER_ON_LEVEL 0` (ONE005 는 1 이 맞음) |
| 시리얼 모니터 글자가 깨짐 | 속도를 **115200** 으로 |
| `error` `BUSY` | 이미 제조 중. 끝날 때까지 기다리거나 `{"cmd":"stop"}` 후 다시 |
| 컴파일 오류 `ArduinoJson.h: No such file` | 라이브러리 매니저에서 ArduinoJson 설치 |
| 컴파일 오류 `JsonDocument` 관련 | ArduinoJson **6.x** 가 깔려 있음 → **7.x** 로 업데이트 |
| 컴파일 오류 BLE 관련 (`getValue`, `String` 변환 등) | ESP32 보드 패키지가 2.x → **3.x** 로 업데이트. `문서/Arduino/libraries` 에 옛 "ESP32 BLE Arduino" 라이브러리가 있으면 삭제 |
| `Sketch too big` | Partition Scheme → Huge APP |

## 10. PC 단위 테스트 (펌웨어 로직 검증)

`BartenderCore.h` 는 하드웨어와 분리되어 있어서 PC 에서 **가짜 시계(1ms 단위)** 로 돌려 볼 수 있습니다.
`test/host_test.cpp`(펌프 4개, **180개**)와 `test/host_test_8.cpp`(펌프 8개로 컴파일, **11개**) 합계 **191개 케이스**가 있고,
2026-11-07 기준 **191/191 통과**했습니다(MSVC 2022, 경고 0). 두 파일이 쓰는 가짜 하드웨어·표 출력 도우미는 `test/test_util.h` 에 있습니다.

주요 케이스:
- 명령별 정상 응답(info 의 `calSet`·`maxPumpMs` 포함), 부팅 시 NVS 저장 여부 → `calSet`, setcal 후 `calSet` = 1, 오류 시 그대로
- 경계값: 0ml / 300ml / 300.1ml, 합계 500 / 500.1ml, steps 8 / 9개, p = 0 / 5 / 1.5 / "1"
- **검증 순서**: mode 오류 + p 오류 → `BAD_JSON`, 9개 + p 오류 → `LIMIT`, step1 ml 오류 + step2 p 오류 → `BAD_AMOUNT` 등
- **같은 펌프 합산**: 200+200 → `LIMIT`, 150+150 = 300 → 통과, 150.1+149.9 → 통과(소수 오차 처리)
- **120초 경계**: 유량 0.5 에서 60ml = 120초 → ack 후 끝까지 실행(감시 오작동 없음), 60.1ml → `LIMIT`
- **run 60초 경계**: 60000 → ack 후 끝까지 실행, 60000.4 / 60001 → `LIMIT`, ms 0 / -1 / "1000" → `BAD_AMOUNT`
- 안전 감시: run 61초 / make 121초 / clean 31초 이상 멈춤 → `stopped(error)` + `LIMIT`, 그 직전(60.999초 등)은 정상 완료
- 순차·병렬(0.1초 간격) 펌프 ON/OFF 시각, 정지 시 추출량 추정, 1024 / 1025 바이트, 20바이트 조각 수신, 괄호 닫힘 판정
- 괄호로 끝난 메시지 뒤 남은 글자(오타 `}` 등) 버림 → 이어서 줄바꿈 없이 보낸 `stop` 정상 처리, 줄바꿈 뒤에는 기존처럼 `BAD_JSON`
- `UNKNOWN_CMD` 오류 메시지가 한글 cmd 를 글자 중간에서 자르지 않음(이벤트가 항상 올바른 UTF-8)
- **millis() 오버플로**(49.7일): 0 을 넘어가는 도중에도 타이밍·추출량이 정확한지
- **status 의 `last`**(v2.1): 부팅 직후 `null`, make 완료 후 `done`+목표량, stop 후 `stopped`+`user`+stopped 이벤트와 글자까지 같은 `dispensed`,
  버튼 정지 `button`, 안전 감시 정지 `error`, run·clean 의 `kind`, 검증 오류·`BUSY`·대기 중 stop 은 `last` 를 안 바꿈,
  제조 중 `status` 에는 직전 작업의 `last`
- **버튼 다시 만들기**(`repeatLast`): 새 id `btn`+ms 로 ack·done, 끝난 뒤 `status.last.id` 가 원래 id 와 다름, 두 번째도 또 새 id, 제조 중이면 `BUSY`, 앱 제조 전이면 아무 일 없음
- **제어문자 id·cmd**: `\u0001`·`\u001f`·`\t`·`\n`·날것 0x01 바이트 → `?` 로 바꿔 모든 이벤트(ack~done, 이후 idle status 3종, UNKNOWN_CMD)가
  **엄격한 JSON**(`test_util.h` 의 `strictJson`, 앱 `JSON.parse` 와 같은 규칙. ArduinoJson 파서는 관대해서 따로 둠)으로 통과
- **펌프 8개**(`host_test_8.cpp`): dispensed 8개 + 한글/따옴표 id 40바이트 2개가 들어간 가장 긴 `status` 도 버퍼(640) 안에 완전한 JSON 으로 나오는지(실측 최대 440바이트)

실행 (Visual Studio 2022 의 C++ 도구가 설치된 Windows PC):
```
firmware\test\build_and_run.bat
```

## 11. SPEC 에 없는 세부 동작 (구현상 결정 사항)

| 상황 | 펌웨어 동작 |
|---|---|
| 대기 중 `stop` | 모든 펌프 OFF 재확인 후 `status`(idle) 응답 (`last` 는 그대로) |
| `status` 의 `last` 를 바꾸는 것 | 작업이 **끝날 때만**(done / stopped: 앱 stop·버튼·안전 감시). 검증 오류·BUSY·그 밖의 명령은 안 바꿈. 재부팅하면 `null` |
| `last` 의 키 순서 | `id`, `kind`, `result`, (`reason`), `dispensed` |
| 이벤트가 출력 버퍼(640바이트)보다 김 / 메모리 부족 | 잘라서 보내지 않고 그 이벤트를 버림 + 시리얼 로그(`# 이벤트가 너무 커서…`). 계산상 가장 긴 이벤트도 516바이트라 실제로는 일어나지 않음 |
| `setcal` 성공 | `cal` 이벤트(전체 유량표 + calSet)로 응답, 그 펌프 `calSet` = 1. 제조 중이면 플래시 저장만 작업 종료 후로 미룸(타이밍 보호). 저장이 실패해도 이번 전원이 켜져 있는 동안은 그 값을 사용(재부팅하면 calSet 0) |
| 같은 유량값을 다시 `setcal` | 이미 같은 값이 저장돼 있으면 플래시에 다시 쓰지 않음(수명 보호) |
| `mode` 가 seq/par 가 아님 | `BAD_JSON`. 단 `"mode":null` 은 생략과 같게 봄(seq) |
| `steps` 가 배열이 아님(문자열·객체) | 누락으로 보고 `BAD_AMOUNT` |
| run 에서 p 와 ms 가 둘 다 틀림 | p 를 먼저 검사 → `BAD_PUMP` |
| `id` 가 40바이트 초과 / 없음 / 빈 문자열 | 40바이트로 자름(한글이 글자 중간에서 잘리지 않게) / `"make"` / `"make"` |
| `id`·모르는 `cmd` 에 제어문자(0x01~0x1F, `\t` `\n` 포함) | `?` 로 바꿔서 사용·표시(예: `"t\u0001"` → `"t?"`). ArduinoJson 이 0x01 같은 제어문자를 이스케이프 없이 출력해 앱이 이벤트를 버리고, `last` 에 남아 이후 `status` 까지 깨지는 것을 막음. 앱이 만드는 id(`r`+시각)에는 해당 없음 |
| 버튼 길게 다시 만들기(`BUTTON_REPEAT_LAST 1`)의 id | 원래 레시피 id 가 아니라 새 id `btn`+기동 후 ms (예: `btn123456`). 재료·모드는 마지막으로 앱이 시작한 make 와 같음 |
| ml 소수 처리 | ArduinoJson 이 짧은 소수를 float 정밀도로 읽기 때문에(150.1 → 150.1000061), 0.0001ml 단위로 정리한 뒤 합계를 검사 |
| 구동시간 120초 비교 | 실제로 켜질 시간(정수 ms 로 반올림)으로 비교 |
| 병렬 모드 progress | 켜져 있는 펌프를 돌아가며 250ms 에 1개씩 전송(알림 폭주 방지) |
| 진행률 `pct` | (지금까지 나온 양 합 ÷ 목표량 합) × 100, 완료 전 최대 99 |
| `done` 의 `dispensed` | 목표량(ml). `stopped` 는 구동시간 비율로 추정한 양, 0ml 펌프는 생략 |
| 줄바꿈 없는 메시지 | `{` 로 시작한 JSON 의 괄호가 닫히면 한 메시지로 인정 (테스트 앱 편의) |
| 괄호로 끝난 메시지 바로 뒤의 글자 | 다음 `{` 또는 줄바꿈이 올 때까지 버림(오류 응답 없음). 예: `{"cmd":"ping"}}` 의 마지막 `}` 는 버려지고 그 뒤 `{"cmd":"stop"}` 은 정상 처리. 줄바꿈으로 끝난 뒤의 `[1,2]` 같은 줄은 그대로 `BAD_JSON` |
| 모르는 `cmd` | `UNKNOWN_CMD`, 메시지에 cmd 를 최대 24바이트까지 보여 줌(한글이 글자 중간에서 잘리지 않게) |
| 안전 감시로 강제 정지 | `stopped` 의 reason = `"error"` + `error/LIMIT` ("안전 제한(120초) 초과…") |
| BLE 알림 구독 전 이벤트 | BLE 로 보내지 않고 버림 (시리얼에는 항상 출력). 새로 연결할 때마다 구독 상태를 0 으로 초기화 |
| BLE 라이브러리의 구독 기록(NVS `ble_cccd`) | 코어 3.3.x 가 휴대폰 주소별로 쌓으므로 부팅할 때 비움(비어 있으면 쓰기 없음). 본딩(페어링)을 쓰지 않으므로 영향 없음 |
| 광고 재시작 실패 | 2초마다 다시 시도 |
